# Day 12 理论笔记：Docker 生命周期 / exec

## 1. 生命周期：run / start / stop / restart / rm / ps

**概念**：`docker run` 从镜像创建并启动一个新容器（= create + start）。`docker ps` 列出运行中的容器，`docker ps -a` 列出所有容器（含已停止）。`docker stop` 停止容器（容器仍存在，可再启动），`docker start` 重新启动已停止的容器，`docker restart` 重启，`docker rm` 删除容器（必须先 stop）。`docker exec -it 容器名 命令` 进入运行中的容器执行命令。

**为什么重要**：理解"run 和 start 的区别"是关键——`run` 每次创建全新容器，`start` 是复活已存在的容器。重复 `run` 会留下大量同名冲突的容器。真实运维中：第一次 `run`，之后用 `start/stop` 管理，最后 `rm` 清理。

**踩坑**：`docker run` 一个已存在名字的容器会报错 `name already in use`——要么换名，要么先 `rm` 旧的。`docker rm` 删除的是容器不是镜像，镜像还在。`ps` 不加 `-a` 看不到已停止的容器，很多人以为容器"消失了"，其实还在占着磁盘。

---

## 2. 运行参数：-d / -p / -it / -v

**概念**：`-d` 后台运行（detached，容器在后台跑，终端还给你）；`-p 宿主机端口:容器端口` 端口映射（把容器的服务端口暴露给宿主机/外部）；`-it` 交互模式 + 分配终端（进入容器敲命令）；`-v 宿主机路径:容器路径` 挂载目录（两边共享文件）。

**为什么重要**：四个参数覆盖了容器使用的全部场景。跑服务用 `-d` + `-p`（后台 + 暴露端口），调试用 `-it`（交互进入），共享数据用 `-v`（挂载）。Day 14 会专门讲 `-v` 数据卷。

**踩坑**：`-d` 后台运行的容器，看不到输出，要用 `docker logs 容器名` 看日志。端口映射方向别写反——`-p 8080:80` 是"宿主机 8080 → 容器 80"。`-it` 不加的话，`docker run` 启动的容器可能立即退出（没有前台进程可运行）。

---

## 3. 容器与宿主机的边界

**概念**：容器是隔离的环境——文件系统、进程、网络都独立。容器里 `ls /` 看到的是容器的根目录，和宿主机完全不同；容器里只能看到自己的进程；网络默认通过 NAT 隔离。这种隔离靠 Linux 的 namespace（命名空间）和 cgroup（资源控制）实现。

**为什么重要**：理解隔离边界，才不会犯"在容器里改的文件宿主机找不到"这类困惑。容器一旦删除，容器内的文件全部消失（这正是 Day 14 要解决的数据持久化问题）。`docker exec` 是"钻进运行中的容器"，此时你操作的是容器环境，不是宿主机。

**踩坑**：容器里装的东西、写的文件，`docker rm` 之后就没了，别把重要数据直接存容器里。判断自己"在容器里还是宿主机"看提示符的用户名和主机名——容器里通常是 `root@随机ID`。`exit` 退出的是容器 shell，不是断开 SSH。

---

## 4. exec -it 与 attach 的区别

**概念**：`docker exec -it 容器名 bash` 在运行中的容器里**新开一个进程**（比如 bash），退出这个 bash 不会影响容器主进程，容器继续跑。而 `docker attach 容器名` 是"贴"到容器的主进程上，退出会导致容器停止。

**为什么重要**：这是日常调试容器的标准操作——服务容器用 `-d` 后台跑着，需要进去看看环境、跑个测试脚本时，用 `exec -it` 钻进一个新 bash，看完 `exit` 退出，容器毫发无损。本案例就是：容器 stop 后用 `start` 复活，再用 `exec -it` 进去跑推理脚本。

**踩坑**：`exec` 只能作用于**运行中**的容器，已停止的容器要先 `start`。`exec` 进入后 `exit` 是安全的，但如果是 `run -it` 启动的交互容器，`exit` 会让容器停止（因为主进程就是 bash）。用 `exec` 时容器的主进程（如 `python app.py`）继续运行，不受影响。
