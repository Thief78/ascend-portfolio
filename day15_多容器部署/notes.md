# Day 15 理论笔记：Docker 多容器综合

## 1. 单容器局限：推理服务 + 前端需协同

**概念**：单容器只能跑一个主进程。真实应用是多个服务协同——推理服务、前端、数据库、缓存各自独立。把这些塞进一个容器违反"一容器一进程"的最佳实践。多容器架构让每个服务独立部署、独立更新、独立扩缩容。

**为什么重要**：昇腾 FAE 交付的推理系统通常是"前端 + 推理后端"分离。推理服务要更新模型时，只重建推理容器，前端容器不受影响。这是微服务思想的雏形——单一职责、独立演进。

**踩坑**：把多个服务塞进一个容器，会导致"改前端要连带重启推理"、日志混在一起难排查、一个服务崩溃拖垮全部。容器不是虚拟机，别想着"一个容器装全套"。

---

## 2. 多容器互联：自定义网络 / docker-compose

**概念**：`docker network create 网络名` 创建自定义网络，容器通过 `--network 网络名` 加入。同一网络内的容器可以用**容器名当域名**互相访问（Docker 内置 DNS 自动解析）。`--link` 是老式互联方式，现已淘汰。docker-compose 是更高级的编排工具，用 YAML 文件定义多个服务及其网络关系，一条命令启动整个服务组。

**为什么重要**：自定义网络是容器通信的现代标准——容器名解析免去手动管理 IP。docker-compose 则是生产环境多容器部署的事实标准，Day 19 端到端交付会用到。

**踩坑**：容器必须在**同一个网络**里才能用容器名互访，默认网络之间是隔离的。`--link` 已过时，新项目不要再用。容器名在网络内必须唯一，重复会报错。

---

## 3. 容器间通信：网络命名空间、端口暴露

**概念**：每个容器有独立的网络命名空间（自己的 IP、端口、路由）。容器默认不与外界通信，需要通信时：同网络容器直接互访（内部端口互通），对外提供服务则用 `-p 宿主机端口:容器端口` 暴露端口。本案例中推理服务在容器内监听 8000，前端容器在**同一网络内**直接用 `http://infer-svc:8000` 访问，无需端口映射——端口映射只在"外部要访问"时才需要。

**为什么重要**：理解"容器内部互通 vs 对外暴露"的区别，才能正确设计网络。内部服务互相调用走容器网络（不需要 `-p`），只有用户/外部系统访问的入口才映射端口。这符合最小暴露原则。

**踩坑**：容器内监听 `127.0.0.1` 而非 `0.0.0.0` 会导致其他容器无法访问（本案例 serve.py 特意用 `0.0.0.0`）。容器间通信不要用宿主机 IP，容器名才是稳定的方式（容器重启 IP 会变，名字不变）。

---

## 4. 多容器部署实践要点

**概念**：本案例的完整链路——创建网络 `infer-net` → 推理容器 `infer-svc` 后台运行加入网络 → 前端容器临时启动加入同一网络 → 用 `http://infer-svc:8000` 调用推理接口 → 清理容器和网络。模拟了真实部署中"服务间通过服务名互调"的核心模式。

**为什么重要**：这是从"会跑单个容器"到"会部署一个系统"的跨越。FAE 交付的多容器推理系统，本质就是本案例的放大版——用 docker-compose 管理多个容器 + 自定义网络 + 服务名互调。

**踩坑**：后台运行的容器（`-d`）要看日志用 `docker logs 容器名`，否则服务挂了你都不知道。`docker network rm` 前必须先把网络内的容器全部删除，否则报错。清理时容器和网络的删除顺序不能乱：先 stop/rm 容器，再 rm 网络。
