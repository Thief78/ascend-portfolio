# Day 18 理论笔记：异构计算 + 性能排查

## 1. 异构计算：CPU vs GPU/NPU 分工

**概念**：CPU 擅长逻辑控制、分支、串行任务，是系统的"总指挥"。GPU/NPU 擅长大规模并行矩阵运算，是 AI 的"算力担当"。异构计算就是让不同架构的处理器协同工作——CPU 负责调度和数据搬运，GPU/NPU 负责密集计算。AI 推理的本质是海量矩阵乘法，天然适合并行，所以必须靠异构架构加速。

**为什么重要**：理解分工才能理解性能瓶颈。推理慢时，如果是 CPU 在干 NPU 的活（比如没正确调用加速卡），性能会差几十倍。昇腾 FAE 的日常工作就是确保模型正确跑在 NPU 上，而不是回退到 CPU。

**易错点**：误以为"程序跑起来就是用上了 GPU/NPU"——实际上如果驱动、框架、算子任一环节没配好，代码可能静默回退到 CPU 执行，速度慢但不出错，非常隐蔽。排查时先确认芯片利用率是否被真正打满。

---

## 2. 昇腾 NPU 基础：910B / 310P 定位

**概念**：昇腾 NPU 是华为的 AI 算力芯片。910B 是训练/推理高端芯片（数据中心级，对标高端 GPU），310P 是推理/边缘芯片（功耗低，适合边缘部署）。NPU 有自己的内存层级——片上缓存、HBM 高带宽内存等。访存瓶颈指"算得快但数据供不上"，很多推理任务实际卡在内存带宽而非算力。

**为什么重要**：昇腾 FAE 要为客户选型——训练场景用 910B，边缘推理用 310P。理解不同芯片的定位和内存层级，才能判断一个模型"能不能塞进这个设备、瓶颈会卡在哪"。

**易错点**：芯片算力强不等于推理快——如果模型太大、访存频繁，瓶颈会卡在内存带宽而非算力。判断瓶颈要看利用率、显存、IO 多个指标，不能只看算力一项。

---

## 3. nvidia-smi / npu-smi 看什么

**概念**：`nvidia-smi`（NVIDIA）和 `npu-smi info`（昇腾）是加速卡的监控命令，核心看三个指标——利用率（芯片忙不忙，100% 表示满载）、显存/内存（用了多少，超限就 OOM）、温度（过热会降频甚至宕机）。`nvidia-smi --query-gpu=... --format=csv` 可以精确提取指定指标。

**为什么重要**：这是 AI 开发者的第一诊断工具。模型报 OOM 时第一眼看显存占用，推理慢时第一眼看利用率。昇腾环境用 `npu-smi info` 看 NPU 状态，是 FAE 排查性能问题的起点。

**易错点**：利用率低但任务慢，说明瓶颈不在算力（可能在 IO 或通信）。显存占满会直接 OOM 崩溃，但显存"看起来够"也可能因为碎片化导致分配失败。温度长期过高会触发芯片降频保护，性能突然下降要查温度。

---

## 4. 性能排查思路：算力 / 显存 / IO / 通信

**概念**：推理慢的瓶颈在四个地方之一——算力（芯片忙满，加卡或换强卡）、显存（内存不够，减 batch 或换小模型）、IO（读数据慢，数据在磁盘没缓存）、通信（多卡间传数据慢，网络或互联带宽不足）。系统级优化就是先定位瓶颈在哪，再对症下药。

**为什么重要**：这是"系统级优化"的方法论，也是岗位图谱的核心要求。盲目优化是浪费——算力瓶颈却去加内存，毫无作用。先监控、定位，再优化。本案例的监控脚本监控 CPU/内存/磁盘/进程，就是定位瓶颈的工具。

**易错点**：四个瓶颈常互相掩盖——IO 慢会让 CPU 利用率"看起来低"，但换更快的芯片没用。多卡场景下单卡数据通信慢会拖累整体，但单卡监控看不出问题。排查要系统化，不能只看单一指标。
