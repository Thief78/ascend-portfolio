# Day 16 理论笔记：深度学习框架 + HTTP

## 1. 框架定位：PyTorch / TensorFlow / MindSpore

**概念**：PyTorch（Meta）、TensorFlow（Google）、MindSpore（华为）都是深度学习框架，用于训练和运行神经网络。它们的关系是竞争+共存——PyTorch 是研究界主流（灵活易用），TensorFlow 是工业界老牌（部署生态成熟），MindSpore 是昇腾生态原生框架（配合华为 NPU 优化）。相关概念：训练（喂数据调整模型参数）、推理（用训练好的模型处理新数据）、checkpoint（训练产物，模型的"权重文件"，`.pt`/`.pth`/`.ckpt`）。

**为什么重要**：昇腾 FAE 的核心就是围绕 MindSpore + CANN + 昇腾 NPU 的推理部署。理解"训练产出 checkpoint → 推理加载 checkpoint → 对外提供推理服务"这条链路，是理解整个精英班目标岗位的基础。

**易错点**：训练和推理是两件事——训练需要 GPU 集群和大量时间，推理只需要加载训练好的权重。checkpoint 文件很大（几百 MB 到几 GB），部署时要正确拷贝。不同框架的 checkpoint 不能通用，PyTorch 训练的模型不能直接被 MindSpore 加载（需要转换工具）。

---

## 2. 昇腾生态：MindSpore 与 CANN / NPU 的关系

**概念**：昇腾 NPU（如 910B、310P）是华为的 AI 算力芯片，类比 GPU。CANN 是昇腾的异构计算架构（类比 CUDA），是芯片之上的软件栈。MindSpore 是深度学习框架（类比 PyTorch），调用 CANN 接口，最终在 NPU 上执行。层级关系：MindSpore → CANN → NPU。

**为什么重要**：开学后会学 CANN 工具链。现在理解"框架 → 计算架构 → 芯片"三层关系，能为后续学习打底。FAE 排查问题时，需要知道问题出在哪一层——是框架代码、CANN 调度、还是 NPU 硬件。

**易错点**：NPU 和 GPU 的软件栈不通用——CUDA 写的代码不能在 NPU 直接跑，需要 MindSpore/CANN 适配。这也是昇腾 FAE 存在的原因：帮客户把 GPU 模型迁移到 NPU 上跑通。

## 3. HTTP 协议：请求方法、状态码、Header/Body、REST

**概念**：HTTP 请求方法——`GET` 获取资源、`POST` 提交数据、`PUT` 更新、`DELETE` 删除。状态码——`2xx` 成功（200 OK、201 Created）、`3xx` 重定向、`4xx` 客户端错误（400 请求格式错、404 资源不存在）、`5xx` 服务端错误（500 内部错误、503 服务不可用）。Header 是请求/响应的元信息（如 `Content-Type: application/json`），Body 是实际传输的数据。REST 风格是"用 URL 定位资源 + 用 HTTP 方法表达操作"的设计约定。

**为什么重要**：推理服务对外交互全靠 HTTP。看状态码能立即判断问题归属——4xx 是调用方的问题（参数错、路径错），5xx 是服务端的问题（服务挂了）。本案例测试了 200/400/404 三种状态码，这是接口测试的基本功。

**易错点**：`GET` 请求不应携带 Body（虽然技术上能带，但违反规范）。状态码记错会误判故障——404 是"路径不存在"，500 是"服务内部崩了"，两者处理方式完全不同。`Content-Type` 设错（如发了 JSON 但标成 text）会导致服务端解析失败。

---

## 4. 推理服务为何走 HTTP 接口

**概念**：模型推理是 Python 写的，但调用方可能是 Java 后端、Go 网关、前端 JS、甚至另一台物理机。HTTP 是跨语言、跨机器的通用协议——任何语言都能发 HTTP 请求，不用管服务端用什么实现。这就是"解耦"：推理服务的实现可以随意换（换框架、换模型），只要接口（URL + 请求/响应格式）不变，调用方无感知。

**为什么重要**：这是推理服务部署的行业标准模式——模型封装成 HTTP 服务，前端/业务系统通过接口调用。昇腾 FAE 交付的推理系统，对外暴露的就是 HTTP 接口。理解这一点，才能理解 Day 19 端到端交付的架构。

**易错点**：接口一旦上线就不能随意改——改了请求格式，所有调用方都会挂。接口设计要"向后兼容"（加字段可以，删字段不行）。健康检查接口（`/health`）是运维标配，监控系统靠它判断服务死活，推理服务必须提供。
